# Gitルール

## 1. 基本方針

- 作業内容を後から確認できる状態にする
- 仕様変更や判断内容は、チャットだけでなくIssueにも残す


## 2. Issueの作成ルール

### Issueを作成する作業

以下の作業の際にはissueを作成してから作業を行う。

- 新機能の追加
- 既存機能の変更
- 不具合の修正
- 調査が必要な問題
- 複数のファイルに影響するリファクタリング

以下の作業の際には、Issueを作成しなくてもよい。

- 誤字脱字の修正
- コメントの修正
- コードの挙動に影響しない小さな整理
- 数分で完了し、相談が不要な修正

### Issueのタイトル

```
機能追加：勤怠管理_概要グラフ追加
バグ修正：ログイン失敗時にエラーが表示されない
改善：勤怠修正時の複数テーブル処理をサービスクラスに分離する
```

「修正」「対応」だけのような、内容が分からないタイトルは避ける。

### Issueの本文

GitHubのIssue Template機能を用いて作成する。

```markdown
## 概要

何を行うIssueなのかを書く。

## 背景・目的

## 作業内容

## 補足

参考資料、検討事項、関連Issueなどがあれば書く。
```

小さな作業ではすべて埋めなくて良いが、「何をするか」は記載する。

---

## 3. Issueのラベル

ラベルは必要最低限とする。（AIの叩き台ママの為、適宜改善）

| ラベル              | 用途             |
| ---------------- | -------------- |
| `feature`        | 新機能の追加         |
| `bug`            | 不具合の修正         |
| `improvement`    | 既存機能の改善        |
| `refactor`       | 挙動を変えないコード整理   |
| `documentation`  | READMEや設計資料の修正 |
| `question`       | 調査や相談          |
| `priority: high` | 優先度が高い作業       |

ラベルを細かく増やしすぎない。

---

## 4. Issueの担当と進捗

作業を開始するときは、次の対応を行う。

1. 自分を担当者に設定する
2. Issueに作業開始を記録する
3. 対応するブランチを作成する

```text
対応を開始します。
```

作業中に仕様や方針が変わった場合は、Issueに理由を記録する。

```text
残業時間について、さきほど法律が変わったためそれに合わせて上限を撤廃します。
```

作業を中断する場合も、現在の状況を残す。

```text
残業時間超過の警告表示撤去を完了しました。
次回は残業時間の概念を無くす作業から再開します。
```

## 5. ブランチ名

ブランチ名は、作業の種類・Issue番号・概要の順で付ける。

```text
feature/12-add-worktime-counter
fix/18-login-error-message
refactor/25-extract-kintai-modify-service
docs/30-update-readme
```

使用する接頭辞は次のとおり。（AIママ）

| 接頭辞        | 用途          |
| ---------- | ----------- |
| `feature`  | 新機能         |
| `fix`      | 不具合修正       |
| `refactor` | リファクタリング    |
| `docs`     | ドキュメント      |
| `test`     | テスト         |
| `chore`    | 設定変更やその他の作業 |

Issueがない軽微な修正では、Issue番号を省略してもよい。

```text
docs/fix-readme-typo
```

## 6. コミットメッセージ

何を変更したかが分かるように日本語で書く。

基本形式は次のとおり。

```text
種類: 変更内容
```

例：

```text
feat: 勤怠登録機能を追加
fix: ログイン失敗時のエラー表示を修正
refactor: 勤怠修正処理をサービスクラスに分離
docs: READMEに環境構築手順を追加
test: 登録処理のテストを追加
chore: RuboCopの設定を変更
```

使用する種類は次のとおり。

| 種類         | 用途           |
| ---------- | ------------ |
| `feat`     | 新機能          |
| `fix`      | 不具合修正        |
| `refactor` | 挙動を変えないコード整理 |
| `docs`     | ドキュメント       |
| `test`     | テスト          |
| `style`    | 空白や整形など      |
| `chore`    | 設定変更や雑務      |

### コミットの単位

後から取り消せる程度のまとまりにする。

良い例：

```text
feat: 残業時間のモデルを追加
feat: 残業時間修正画面を追加
test: 残業時間validateのテストを追加
```

避ける例：

```text
いろいろ修正
作業途中
変更
完成
```

作業途中のコミットをリモートに保存する必要がある場合は、次のように書いてもよい。

```text
wip: 勤怠修正画面を変更中
```

ただし、Pull Requestをマージする前に、可能であればコミットを整理する。

```text
feat: 残業時間のモデルを追加
fix: バグ修正
fix: さらに修正
↓
feat: 残業時間算出機能を追加
```

## 7. Pull Requestのコメント

Pull Requestを作成するときは、関連するIssueを記載する。

```markdown
## 概要

勤怠を登録できるようにしました。

## 対応内容

- 勤怠時間モデルを追加
- 登録画面を追加
- バリデーションを追加

## 確認方法

1. ログインする
2. ヘッダーの勤怠登録を押す
3. 出勤退勤ボタンを押す
4. 登録一覧に表示されることを確認する

## 関連Issue

Closes #12

## 補足

画面デザインは今後調整予定です。
```

Issueを自動的に閉じる場合は、次のいずれかを使用する。

```text
Closes #12
Fixes #12
Resolves #12
```

## 8. レビューコメント

レビューコメントでは、修正必須か提案かを区別する。

```text
[必須]
このままだと未ログイン時にエラーになるため、nilの場合の処理を追加してください。
```

```text
[提案]
処理をメソッドに分けると、読みやすくなりそうです。
```

```text
[質問]
この値を5分キャッシュする理由を教えてください。
```

```text
[細かい点]
変数名をwork_dataにすると、内容が分かりやすいと思います。
```

人ではなく、コードや挙動を対象にコメントする。

避ける表現：

```text
書き方が悪いです。
なぜこんな実装にしたのですか。
```

推奨する表現：

```text
この処理は複数の責務を持っているため、取得処理と保存処理に分けると読みやすくなりそうです。
```

レビュー対応後は、修正内容を返信する。

```text
ご指摘ありがとうございます。
nilの場合は処理を終了するように修正しました。
```

対応しない場合は、その理由を返信する。

```text
今回は同じ処理をほかで使用する予定がないため、メソッドへの分離は行わない方針とします。
処理が増えた段階で改めて検討します。
```

---

## 9. マージルール

- 原則として、Pull Requestを作成してからマージする
- 動作確認の方法をPull Requestに記載する
- マージ後は、不要になったブランチを削除する

軽微な誤字修正などは直接マージしてもよい。

---

## 10. Issueを閉じる条件

次の条件を満たしたらIssueを閉じる。

- 実装または修正が完了している
- 必要な動作確認が完了している
- Pull Requestがマージされている
- 残作業がある場合は、別のIssueが作成されている

仕様変更などにより対応しない場合は、理由をコメントして閉じる。

```text
現在の仕様ではこの機能を使用しない方針となったため、対応せずにクローズします。
必要になった場合は、新しいIssueとして再検討します。
```

---

## 11. 小規模チーム向けの例外(AI提案)

2〜3人の小規模チームでは、運用そのものが負担にならないことを優先する。

- 小さな修正ではIssueを省略できる
- Pull Requestの本文は短くてもよい
- 自分だけで完結する作業でも、重要な判断は記録する
- 口頭やチャットで決まった仕様変更は、IssueまたはPull Requestに転記する
- ルールが実態に合わない場合は、チームで相談して変更する
